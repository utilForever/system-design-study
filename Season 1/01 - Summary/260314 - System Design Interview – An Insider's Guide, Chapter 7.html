요구사항 정의

기능적 요구사항
  • 유일성: ID는 전역적으로 유일해야 함
  • 숫자형: 숫자만 포함
  • 64비트: 64비트 크기 제한
  • 시간순 정렬: 생성 시간에 따른 정렬 가능
  • 고성능: 초당 10,000개 이상 생성
비기능적 요구사항
  • 고가용성: mission-critical 시스템 (Step 4)
  • Clock 동기화: NTP 등 고려 (Step 4)
  • 섹션 길이 튜닝: 용도별 비트 조정 (Step 4)

방법 1: Multi-master Replication

DB의 auto_increment를 활용하되, 1 대신 k(서버 수)만큼 증가시킨다.
서버가 2대이면 하나는 홀수(1,3,5…), 다른 하나는 짝수(2,4,6…)를 생성한다.

Server 2
짝수: 2, 4, 6…
↓
Web App 2
생성된 ID

장점 👍

DB auto_increment 기능 활용
서버 수만큼 ID 확장 가능
일부 확장성 문제 해결

단점 👎

  • ✗여러 데이터 센터 확장 어려움
  • ✗시간순 ID 증가 보장 안됨
  • ✗서버 추가/제거 시 k값 변경 필요 → 확장 어려움

최종 선택: Twitter Snowflake

모든 요구사항을 만족하는 유일한 방안

앞선 방법들은 각각 한계가 있었다: Multi-master는 시간순 정렬 불가, UUID는 128비트·비숫자형, Ticket Server는 SPOF.
이 모든 요구사항을 만족하는 새로운 접근이 필요하다 — Twitter가 개발한 Snowflake는
"분할 정복" 전략으로 64비트 ID를 여러 섹션으로 나누고, 각 머신이 DB 조회 없이 메모리에서 독립적으로 ID를 생성한다.
