## 처리율 제한 장치란?

> 클라이언트 또는 서비스가 보내는 트래픽의 처리율을 제어 하기 위한 장치

### 처리율 제한 장치의 장점

1. DoS 공격에 의한 자원 고갈을 방지(과용)
2. 인프라 비용 절감
3. 서버 과부화를 방지(오용)

### 처리율 제한 장치가 가능한 위치

1. 클라이언트 - 쉽게 위변조가 가능하다는 단점을 지님
2. 서버
3. 클라이언트와 서버의 중간에 미들웨어
  a. 클라우드 마이크로 서비스의 경우 보통 API 게이트웨이에 SSL 종단, 사용자 인증, IP 허용목록 관리 등과 함께 구현

### 처리율 제한 장치를 어디에 둬야 하나? -> 답은 없다

#### 하지만 고려해야 할 사항

1. 현재 사용하고 있는 프로그래밍 언어 등 기술 스택
2. 처리율 제한 알고리즘
3. 아키텍처
  a. 사용자 인증이나 IP 허용목록 관리 등을 API 게이트웨이에 포함되었다면 여기에 포함시켜야 할 수도 있다.
4. 구현할지, 상용 서비스를 사용할지

### 처리율 제한 알고리즘

1. 토큰 버킷
  - 일정 시간마다 채워지는 토큰이 버킷에 있을 경우 사용가능, 토큰이 있다면 동시에 요청가능
  - 장점: 구현이 쉽다.
  - 단점: 버킷 크기와 토큰 공급률 외에는 튜닝이 힘들다. 
2. 누출 버킷
  - FIFO 구조로 토큰 버킷과 달리 처리율이 고정되어 있다.
  - 장점: 고정된 처리율오 안정적인 출력에 적합
  - 단점: 단시간에 트래픽이 몰리는 경우 오래된 요청들이 쌓이고 제때 처리 못하면 최신 요청들이 버려진다.
3. 고정 윈도 카운터
  - 타임라인을 고정된 간격의 윈도우로 나누고 각 윈도우가 처리할 수 있는 양이 정해져 있다.
  - 장점: 메모리 효율이 좋다.
  - 단점: 윈도우 경계 부근에 일시적으로 많은 트래픽이 몰릴 경우 기대보다 많은 요청을 처리하게 된다.
4. 이동 윈도 로그 -> 자세한 알고리즘을 봐야 할듯!
  - 고정 윈도 카운터에서 윈도 경계 부근에 트래픽이 집중되는 것을 해결함
  - 장점: 어느 순간의 윈도우를 보더라도 허용되는 요청의 개수는 시스템 처리율 한도를 넘지 않는다.
  - 단점: 거부된 요청의 타임라인도 저장하기 때문에 메모리 사용량이 많다.
5. 이동 윈도 카운터
  - 고정 윈도 카운터 알고리즘과 이동 윈도 로깅 알고리즘을 결합한것.
  - 장점: 요청 처리가 안정적이다.
  - 단점: 타 알고리즘에 비해 어려운 구현?

### 카운터를 어디에 저장할 것인가?

  - 디스크상의 데이터베이스는 느림
  - 속도때문에 인메모리상에서 처리해야 함
  - 시간 만료 정책을 지원하는 캐쉬가 바람직 -> Redis

### 처리율 제한 장치 서버가 여러대 일경우 아래 문제가 발생

1. 경쟁 조건
  - 멀티 쓰레드 환경처럼 카운터 값이 제대로 계산 안됨
  - 기본적인 해결방법: Lock, 하지만 성능 저하 발생
2. 동기화 이슈
  - 특정 클라이언트의 카운터가 어느 처리율 제한 장치 서버에만 있을 경우 다른 제한 장치 서버에 요청하면 올바른 제한이 되지 않는다.
  - 기본적인 해결방벙: 고정 세션을 활용하여 같은 클라이언트로부터의 요청은 항상 같은 처리율 제한 장치로 보낼 수 있지만 스케일 아웃측면에서 좋지 않다.
