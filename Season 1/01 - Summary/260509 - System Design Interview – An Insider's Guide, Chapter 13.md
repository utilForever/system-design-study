# 검색어 자동완성 시스템 설계

## 1. 검색어 자동완성 시스템의 이해

검색어 자동완성 시스템은 사용자가 검색창에 일부 문자열을 입력하는 순간, 입력 중인 문자열을 접두어(prefix)로 갖는 인기 검색어를 추천해주는 시스템이다. 예를 들어 사용자가 `chat`을 입력하면 `chatgpt`, `chatbot`, `chat application`과 같은 후보를 빠르게 보여준다.

이 시스템의 목적은 단순히 문자열을 이어 붙여 예측하는 것이 아니라, 사용자가 실제로 검색할 가능성이 높은 검색어를 낮은 지연 시간 안에 제공하는 것이다. 따라서 자동완성 시스템은 문자열 검색, 검색어 빈도 집계, 랭킹, 캐싱, 필터링, 다국어 처리, 지역별 개인화 등 여러 요소가 결합된 시스템이다.

### 1.1 핵심 기능 요구사항

1. 사용자가 입력한 문자열과 연관된 단어를 출력해야한다.
2. 응답은 빠르게 제공되어야 한다. (책에서 제시된 수치로는 100ms)
3. 한번에 표시되는 자동완성 검색어는 5개
4. 검색어 노출 순서는 질의 빈도에 따라 정해지는 인기 순위
5. 맞춤법 검사기능이나 자동 수정
6. 많은 트래픽을 감당할 수 있도록 확장 가능해야한다.
7. 시스템 일부에 장애가 발생하거나 / 지연 및 네트워크 문제에도 계속 사용 가능해야한다.

### 1.2 개략적인 규모 가정

책에서는 다음과 같은 규모의 서비스를 가정하고 있다.

- 일간 활성 사용자: 1천만 명
- 사용자 1명당 하루 평균 검색 횟수: 10회
- 검색당 사용 데이터 : 20바이트 (4개 단어, 평균적으로 단어당 5글자)
- 검색당 평균 백엔드 요청 횟수 : 20회
- 평균 QPS 및 최대 QPS : 24,000 (최대 48,000)
- 질의중 20%는 신규 검색어

## 2. 검색어 자동완성 아키텍처 설계

## 2.1 개략적인 설계

자동완성 시스템은 크게 두 가지 흐름으로 나눌 수 있다.

1. **데이터 수집 경로**  
   사용자가 검색한 검색어를 로그로 수집하고, 검색어별 사용 빈도를 계산한다.

2. **쿼리 서비스 경로**  
   사용자가 검색창에 문자열을 입력하면, 해당 문자열을 기반으로 추천 검색어를 조회해 반환한다.

개략적인 구성은 다음과 같다.

```text
[사용자 검색]
     |
     v
[검색 서비스] -----> [검색 로그 저장소]
                         |
                         v
                  [집계 작업 / 워커]
                         |
                         v
                 [검색어 빈도 저장소]
                         |
                         v
[사용자 입력] ---> [자동완성 API] ---> [추천 결과 반환]
```

### 2.1.1 단순한 데이터베이스 기반 접근

가장 단순한 설계는 검색어와 검색 빈도를 관계형 데이터베이스에 저장하고, 사용자가 입력한 문자열을 접두어로 갖는 검색어를 조회하는 방식이다.

예를 들어 다음과 같은 테이블을 둘 수 있다.

```sql
CREATE TABLE search_terms (
    term VARCHAR(255) PRIMARY KEY,
    frequency BIGINT NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

사용자가 `app`을 입력하면 다음과 같이 조회할 수 있다.

```sql
SELECT term, frequency
FROM search_terms
WHERE term LIKE 'app%'
ORDER BY frequency DESC
LIMIT 5;
```

이 방식은 이해하기 쉽고 초기 구현이 빠르다. 하지만 데이터가 커지고 요청량이 많아지면 문제가 생긴다.

- 짧은 prefix일수록 매칭되는 검색어가 너무 많다.
- `LIKE 'prefix%'` 쿼리는 인덱스를 활용할 수 있더라도 대규모 트래픽에서는 부담이 크다.
- 매 입력마다 DB를 조회하면 DB가 병목이 된다.
- 랭킹 기준이 단순 빈도 이상으로 복잡해지면 쿼리 비용이 커진다.

따라서 대규모 시스템에서는 쿼리 시점에 DB에서 후보를 매번 계산하기보다는, 미리 계산된 자료구조를 메모리나 캐시에 올려두고 빠르게 조회하는 방향으로 설계한다.

## 2.2 상세 설계

## 2.2.1 문자열 쿼리를 처리하는 트라이

자동완성 시스템에서 대표적으로 사용되는 자료구조는 **트라이(Trie)** 이다. 트라이는 문자열을 문자 단위로 나누어 트리 형태로 저장하는 자료구조다. 루트에서 특정 노드까지의 경로가 하나의 접두어를 의미한다.

예를 들어 `app`, `apple`, `application`, `bee`를 저장한 트라이는 다음과 같이 표현할 수 있다.

```text
(root)
 ├── a
 │   └── p
 │       └── p   [app]
 │           └── l
 │               ├── e   [apple]
 │               └── i
 │                   └── c
 │                       └── a
 │                           └── t
 │                               └── i
 │                                   └── o
 │                                       └── n [application]
 └── b
     └── e
         └── e [bee]
```

사용자가 `app`을 입력하면, 먼저 루트에서 `a -> p -> p` 경로를 따라간다. 해당 노드 아래에 있는 단어들이 모두 `app`을 접두어로 갖는 후보가 된다.

### 트라이 조회 과정

1. 입력 문자열의 각 문자를 따라 트라이를 내려간다.
2. 입력 문자열에 해당하는 노드에 도달한다.
3. 해당 노드의 하위 서브트리에서 검색어 후보를 찾는다.
4. 후보를 빈도 또는 점수 기준으로 정렬해 상위 K개를 반환한다.

### 시간 복잡도

입력 문자열 길이를 `p`, 후보 개수를 `c`, 반환할 추천어 수를 `k`라고 하자.

단순한 트라이에서는 다음 비용이 든다.

- prefix 노드 탐색: `O(p)`
- prefix 아래 후보 수집: `O(c)`
- 후보 정렬: `O(c log c)` 또는 상위 K개만 유지하면 `O(c log k)`

문제는 `c`가 매우 클 수 있다는 점이다. 예를 들어 사용자가 `a`만 입력하면 `a`로 시작하는 모든 검색어가 후보가 된다. 따라서 매번 서브트리를 탐색하고 정렬하는 방식은 비효율적이다.

이를 개선하기 위해 각 트라이 노드에 **상위 K개 추천 결과를 미리 저장**할 수 있다.

```text
노드: app
top suggestions:
1. apple        120,000
2. app store     90,000
3. application   70,000
4. apple watch   50,000
5. app design    20,000
```

이렇게 하면 쿼리 시점에는 입력 문자열에 해당하는 노드까지만 이동한 뒤, 해당 노드에 저장된 top K를 바로 반환할 수 있다.

- prefix 노드 탐색: `O(p)`
- 추천 결과 반환: `O(k)`
- 전체 조회 시간: `O(p + k)`

자동완성 시스템에서 `k`는 보통 5 또는 10처럼 작은 값이므로, 사실상 입력 문자열 길이에 비례하는 매우 빠른 조회가 가능하다.

## 2.2.2 매 검색마다 트라이를 갱신하는 방식의 문제

검색어 자동완성은 사용자의 실제 검색 로그를 기반으로 추천 순위를 갱신해야 한다. 단순하게 생각하면 사용자가 검색할 때마다 해당 검색어의 빈도를 증가시키고, 트라이의 관련 노드들을 즉시 갱신할 수 있다.

예를 들어 사용자가 `apple watch`를 검색하면 다음 prefix 노드의 top K가 바뀔 수 있다.

```text
a
ap
app
appl
apple
apple
apple w
apple wa
...
apple watch
```

검색어 길이가 길수록 갱신해야 하는 노드가 많아진다. 또한 각 노드의 top K 목록을 다시 계산하거나 정렬해야 할 수도 있다. 검색 요청이 매우 많은 서비스에서는 매 검색마다 트라이를 즉시 갱신하는 방식이 너무 비싸다.

따라서 일반적으로 검색 로그 수집과 자동완성 조회를 분리한다.

## 2.2.3 로그 기반 집계와 트라이 갱신 구조

대규모 자동완성 시스템은 보통 다음과 같은 구조를 갖는다.

```text
검색 요청 흐름

[사용자]
   |
   v
[검색 서비스]
   |
   +---------------------> [검색 로그 큐]
                            |
                            v
                       [로그 집계 워커]
                            |
                            v
                      [빈도/점수 저장소]
                            |
                            v
                      [트라이 빌더]
                            |
                            v
                    [트라이 데이터베이스]
                            |
                            v
                       [트라이 캐시]
                            |
                            v
[자동완성 API] <---- [캐시된 트라이 조회]
   |
   v
[추천 결과]
```

### 구성 요소 설명

#### 1. 검색 로그 큐

사용자가 검색한 검색어를 바로 DB에 쓰지 않고 로그 큐에 적재한다. Kafka, Kinesis, Pub/Sub과 같은 메시지 큐를 사용할 수 있다. 큐를 사용하면 검색 서비스와 집계 시스템을 느슨하게 결합할 수 있고, 순간적인 트래픽 증가도 버퍼링할 수 있다.

#### 2. 로그 집계 워커

워커는 검색 로그를 일정 주기로 읽어 검색어별 빈도를 집계한다. 집계 단위는 요구사항에 따라 달라질 수 있다.

- 전체 누적 검색 빈도
- 최근 1시간 검색 빈도
- 최근 24시간 검색 빈도
- 국가별 검색 빈도
- 언어별 검색 빈도
- 디바이스별 검색 빈도

단순 누적 빈도만 사용하면 오래된 인기 검색어가 계속 상위에 남을 수 있다. 따라서 최신성을 반영하기 위해 시간 감쇠(time decay)나 최근 기간 가중치를 사용할 수 있다.

예시 점수 계산:

```text
score = 전체 빈도 가중치 + 최근 24시간 빈도 가중치 + 최근 1시간 트렌드 가중치
```

#### 3. 빈도/점수 저장소

집계된 검색어별 점수를 저장하는 저장소다. 관계형 DB, NoSQL, key-value store 등을 사용할 수 있다.

예시 데이터:

| term        | global_count | recent_count | country | language | score |
| ----------- | -----------: | -----------: | ------- | -------- | ----: |
| apple       |      1000000 |        30000 | US      | en       |  0.98 |
| apple watch |       500000 |        20000 | US      | en       |  0.82 |
| 앱스토어    |       300000 |        10000 | KR      | ko       |  0.77 |

#### 4. 트라이 빌더

트라이 빌더는 빈도/점수 저장소를 읽어 자동완성 조회에 최적화된 트라이를 만든다. 각 노드에는 해당 prefix에 대한 상위 K개 추천어가 저장된다.

트라이 빌드는 일정 주기로 수행할 수 있다.

- 매 5분
- 매 1시간
- 하루 1회 전체 빌드 + 실시간 delta 반영
- 책에서는 1주에 한번 빌드를 예시로 들었음

#### 5. 트라이 데이터베이스

빌드된 트라이를 영속적으로 저장하는 곳이다. 자동완성 API 서버가 재시작되거나 캐시가 비워져도 다시 로드할 수 있도록 한다. 트라이는 일반적인 행 기반 DB보다 파일, key-value store, object storage, NoSQL 등에 직렬화하여 저장할 수 있다.

#### 6. 트라이 캐시

실제 쿼리 경로에서는 트라이를 메모리에 올려두거나 Redis/Memcached 같은 캐시에 저장하여 빠르게 조회한다. 자동완성 API는 매 요청마다 원본 DB를 조회하지 않고, 캐시된 트라이를 통해 결과를 반환한다.

## 2.2.4 기타 최적화 방안

### 1. AJAX Request

페이지를 새로 고침할 필요 없이 자동완성에 필요한 문자 변경에만 대응하면 된다.

### 2. 브라우저 캐싱

많은 사용자는 검색했던 결과를 다시 검색하곤 하기 때문에, 브라우저 캐시에 기존 검색 결과들을 저장해두면 실질적인 요청 없이 디바이스 내에서 처리할 수 있게 된다.

### 3. 데이터 샘플링

모든 검색 결과를 모두 로깅하고 처리하는건 많은 자원의 소모가 발생하기 때문에 요청중 일부만 샘플링하게 최적화 할 수 있다

### 4. 트라이 연산 최적화

트라이가 작을때는 트라이 노드를 개별로 갱신하는 방법도 가능

만약 트라이를 샤딩해두었다면 샤드 단위로 갱신할 수도 있을 것 같음

### 5. 요청 제한 및 디바운싱

사용자가 빠르게 타이핑할 때 모든 키 입력마다 요청을 보내면 서버 부하가 커진다. 클라이언트에서 다음 최적화를 적용할 수 있다.

- 100~300ms 디바운싱
- 입력 길이가 1자 미만이면 요청하지 않음
- 이전 요청과 같은 prefix이면 재요청하지 않음
- 네트워크가 느리면 오래된 응답을 버림

## 2.2.5 검색어 필터링

혐오성, 폭력적인 검색어들이나 기타 법적인 (아무튼) 문제를 가진 결과들은 폐기해야한다.

책에서는 쿼리 응답 이전에 필터를 두는 예시를 제공했지만,

다음 DB 업데이트 사이클에도 비동기적으로 삭제하는 내용도 제시했다.

실질적으로는 다음 3가지 지점에서 필터링 할 수 있을 것 같다.

### 1. 로그 수집 단계 필터링

검색 로그를 수집할 때 명백히 부적절한 검색어를 제외한다. 이 방식은 저장소에 불필요한 데이터를 넣지 않는 장점이 있다.

### 2. 트라이 빌드 단계 필터링

트라이를 만들 때 정책에 맞지 않는 검색어를 제외한다. 로그 원본은 분석 목적으로 남기되, 추천 시스템에는 노출하지 않는 방식이다.

### 3. 쿼리 응답 단계 필터링

자동완성 API가 응답을 반환하기 직전에 필터링을 한 번 더 적용한다. 정책이 바뀌었거나 긴급 차단이 필요한 검색어를 빠르게 막을 수 있다.

실무에서는 보통 여러 단계를 함께 사용한다.

## 2.2.6 규모 확장: 샤딩

검색어와 요청량이 많아지면 하나의 트라이 또는 하나의 서버로 모든 prefix를 처리하기 어렵다. 이때 샤딩을 통해 데이터를 나누어 저장하고 조회할 수 있다.

# 3. 더 나아가서

## 3.1 알파벳뿐 아니라 다국어를 지원

영어 자동완성은 알파벳 단위로 비교적 단순하게 처리할 수 있다. 하지만 실제 서비스에서는 한국어, 일본어, 중국어, 아랍어, 힌디어 등 다양한 언어를 지원해야 한다.

### 3.1.1 Unicode 기반 처리

모든 문자열은 Unicode로 정규화해야 한다. 같은 글자처럼 보이더라도 내부 표현이 다를 수 있기 때문이다.

- 모든 유니코드를 다 처리할 것인지

- 유니코드 지원에 따른 트라이의 밀도가 낮아지는데, 트라이 압축하는거 효과적일까?

### 3.1.2 한국어 검색의

- 초성 검색
- 자모 분해 검색
- 띄어쓰기 무시 검색
- 오타 보정
- 영문 입력 상태에서의 한글 변환 후보 처리

### 3.1.3 중국어/일본어

- 중국어 병음 기반 자동완성
- 일본어 히라가나/가타카나/한자 변환
- 형태소 분석 또는 사전 기반 토큰화
- 문자 단위 prefix와 발음 기반 prefix의 병행 지원

### 3.1.4 기타 언어의 특수성

- 뭐가 있을까요

- 이모지 검색되면 재밌을까
