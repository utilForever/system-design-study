# URL 단축기 설계

## 문제 이해 및 설계 범위

### 요약

- 긴 URL이 주어졌을 때, 단축 URL을 결과로 제공해야 함
  - 이 URL에 접속하면 원래 URL로 리다이렉트되어야 함
- 매일 1억개의 단축 URL을 만들어 낼 수 있어야 함
- 길이는 짧을수록 좋음
- 단축 URL에는 숫자와 영문자만 사용할 수 있음
- 시스템에서 삭제하거나 갱신할 수 없음

### 개략적 추정

- 쓰기 연산 : 매일 1억 개의 단축 URL 생성
- 초당 쓰기 연산 : 1억 / 24 / 3600 = 1,157 URL/s
- 읽기 연산 : 읽기 연산과 쓰기 연산의 비율이 10:1이라고 가정하면, 초당 읽기 연산은 11,570 URL/s
- URL 단축 서비스를 10년 동안 운영한다고 가정하면, 총 단축 URL 수는 1억 * 365 * 10 = 3650억 개
- 축약 전 URL의 평균 길이가 100자라고 가정하면, 저장해야 하는 데이터 양은 3650억 * 100 = 36.5TB

## 개략적 설계안 제시 및 동의 구하기

### API 엔드포인트

- REST 스타일로 설계
- URL 단축기는 기본적으로 두 개의 엔드포인트를 제공해야 함

#### URL 단축용 엔드포인트

- HTTP 메서드 : POST
- URL : /shorten
  - 인자 : 원래 URL (예: {"long_url": "https://www.example.com"})
  - 반환값 : 단축 URL (예: {"short_url": "http://short.url/abc123"})

#### URL 리다이렉션용 엔드포인트

- HTTP 메서드 : GET
- URL : /shortUrl
  - 반환값 : 원래 URL로 리다이렉트

### URL 리디렉션

- 단축 URL이 요청되면, 시스템은 해당 단축 URL에 매핑된 원래 URL을 조회해야 함
- 원래 URL이 존재하면, HTTP 301 또는 302 상태 코드와 함께 원래 URL로 리다이렉트
  - 301 Moved Permanently : 단축 URL이 영구적으로 원래 URL로 리다이렉트됨을 나타냄
  - 302 Found : 단축 URL이 일시적으로 원래 URL로 리다이렉트됨을 나타냄
- 301과 302의 차이는 SEO에 영향을 미칠 수 있음
  - 301은 검색 엔진이 원래 URL을 인덱싱하도록 유도하는 반면, 302는 검색 엔진이 단축 URL을 인덱싱하도록 허용함
  - 301은 원래 URL의 검색 엔진 순위를 유지하는 데 도움이 될 수 있지만, 302는 단축 URL이 검색 엔진 순위에 영향을 미칠 수 있음
  - 트래픽 분석이 중요할 경우, 302를 사용하여 단축 URL이 클릭된 횟수를 추적할 수 있음
- 원래 URL이 존재하지 않으면, HTTP 404 Not Found 상태 코드 반환

### URL 단축

- URL 리디렉션을 구현하는 가장 직관적인 방법은 해시 테이블을 사용하는 것임
  - 단축 URL을 키로 사용하고, 원래 URL을 값으로 저장
- 해시 함수의 요구 사항
  - 입력으로 주어지는 긴 URL이 다른 값이면 해시 값도 달라야 함 (충돌 방지)
  - 계산된 해시 값은 원래 입력으로 주어졌던 긴 URL로 복원될 수 있어야 함 (역해시 가능)


## 상셰 설계

### 데이터 모델

- 개략적 설계를 진행할 때는 모든 것을 해시 테이블에 두었지만, 메모리는 한정되어 있기 때문에 관계형 데이터베이스를 사용하여 데이터를 저장하는 것이 더 현실적임
- 데이터 모델은 다음과 같이 정의할 수 있음
  - `id` : 고유 식별자 (자동 증가)
  - `long_url` : 긴 URL (텍스트)
  - `short_url` : 단축 URL (고유, 최대 10자)
  - `created_at` : URL이 생성된 시간 (타임스탬프)

```sql
CREATE TABLE url_mapping (
    id SERIAL PRIMARY KEY,
    long_url TEXT NOT NULL,
    short_url VARCHAR(10) NOT NULL UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 해시 함수

- 해시 함수(Hash Function)는 긴 URL을 단축 URL로 변환하는 데 사용됨

#### 해시 값 길이

- 해시 값은 [0-9a-zA-Z]의 문자 집합을 사용하여 생성됨
- 가능한 조합 수는 62^n (n은 해시 값의 길이)
- 10억 개의 단축 URL을 지원하려면, n이 최소 6이어야 함 (62^6 = 56,800,235,584 > 1,000,000,000)
- 해시 함수 구현에 쓰이는 기술
  - 해시 후 충돌 해소
  - base-62 변환

#### 해시 후 충돌 해소

- 잘 알려진 해시 함수 : CRC32, MD5, SHA-1 등
- 그런데 가장 짧은 해시값조차도 6보다 길어질 수 있음 → 어떻게 짧은 해시값을 만들 수 있을까?
  - 첫 번째 방법 : 처음 6개 글자만 사용
    - 하지만 충돌이 발생할 가능성이 높음
    - 충돌이 실제로 발생했을 때, 충돌이 해소될 때까지 사전에 정한 문자열을 해시값에 덧붙임
    - 이 방법을 쓰면 충돌은 해소할 수 있지만 단축 URL을 생성할 때 한 번 이상 데이터베이스에 질의를 해야 하므로 오버헤드가 큼
    - 데이터베이스 대신 블룸 필터를 사용하면 성능을 높일 수 있음

#### base-62 변환

- 진법 변환은 URL 단축기를 구현할 때 흔히 사용되는 접근법 중 하나
- 62진법을 쓰는 이유는 해시 값에 사용할 수 있는 문자의 수가 62개이기 때문임 (0-9, a-z, A-Z)
- 예시 : 10진수로 11157을 62진수로 변환
  - 11157 / 62 = 179 (몫), 11157 % 62 = 59 (나머지) → 'X' (62진수에서 59에 해당하는 문자)
  - 179 / 62 = 2 (몫), 179 % 62 = 55 (나머지) → 'T' (62진수에서 55에 해당하는 문자)
  - 2 / 62 = 0 (몫), 2 % 62 = 2 (나머지) → '2' (62진수에서 2에 해당하는 문자)
  - 따라서 11157을 62진수로 표현하면 '2TX'가 됨

#### 두 접근법 비교

| 해시 후 충돌 해소 전략 | base-62 변환 |
| ----------------------- | -------------- |
| 단축 URL의 길이가 고정됨 | 단축 URL의 길이가 가변적. ID 값이 커지면 같이 길어짐 |
| 유일성이 보장되는 ID 생성기가 필요치 않음 | 유일성 보장 ID 생성기가 필요 |
| 충돌이 가능해서 해소 전략이 필요 | ID의 유일성이 보장된 후에야 적용 가능한 전략이라 충돌은 아예 불가능 |
| ID로부터 단축 URL을 계산하는 방식이 아니라서 다음에 쓸 수 있는 URL을 알아내는 것이 불가능 | ID가 1씩 증가하는 값이라고 가정하면 다음에 쓸 수 있는 단축 URL이 무엇인지 쉽게 알아낼 수 있어서 보안상 문제가 될 소지가 있음 |

### URL 단축기 상세 설계

1. 입력으로 긴 URL을 받음
2. 데이터베이스에 해당 URL이 있는지 검사
3. 데이터베이스에 있다면 해당 URL에 대한 단축 URL을 만든 적이 있음 → 데이터베이스에서 해당 단축 URL을 가져와서 클라이언트에게 반환
4. 데이터베이스에 없다면 해당 URL은 새로 접수된 것임 → 유일한 ID를 생성한 후 데이터베이스의 기본 키로 사용
5. 62진법 변환을 적용, ID를 단축 URL로 만듦
6. ID, 단축 URL, 원래 URL로 새 데이터베이스 레코드를 만든 후 단축 URL을 클라이언트에 전달

#### URL 리디렉션 상세 설계

1. 사용자가 단축 URL을 클릭
2. 로드 밸런서가 해당 클릭으로 발생한 요청을 웹 서버에 전달
3. 단축 URL이 이미 캐시에 있는 경우에는 원래 URL을 바로 꺼내서 클라이언트에게 전달
4. 캐시에 해당 단축 URL이 없는 경우에는 데이터베이스에서 꺼냄 (데이터베이스에 없다면 사용자가 잘못된 단축 URL을 입력한 경우일 것임)
5. 데이터베이스에서 꺼낸 URL을 캐시에 넣은 후 사용자에게 반환
