## 문제 정의 및 배경

### 실제 시나리오

- 자동 증가 ID는 단일 데이터베이스에서는 잘 작동하지만, 분산 환경에서는 지연과 중복 문제 발생

### 기존 방식의 한계

- **단일 데이터베이스의 auto_increment 사용 불가**
  - 단일 서버 용량의 한계
  - 분산 환경에서 ID 중복 발생 가능성
  - 여러 데이터베이스 간 동기화 문제

### 분산 시스템에서의 도전 과제

- **확장성**: 초당 수천 개의 ID 생성 필요
- **유일성**: 전체 시스템에서 절대 중복 없어야 함
- **가용성**: 일부 서버 장애 시에도 ID 생성 지속
- **성능**: 최소한의 지연 시간으로 ID 생성

[다이어그램: 전통적인 단일 DB vs 분산 시스템 구조 비교]

## 요구사항

### 기능적 요구사항

- ✅ **유일성**: ID는 전역적으로 유일해야 함
- ✅ **숫자형**: 숫자만 포함 (문자 제외)
- ✅ **64비트**: 64비트 크기 제한
- ✅ **시간순 정렬**: 생성 시간에 따른 정렬 가능
- ✅ **고성능**: 초당 10,000개 이상 생성 가능

### 비기능적 요구사항

- **고가용성**: 99.9% 이상 가동률
- **확장성**: 수평적 확장 가능
- **낮은 지연시간**: 밀리초 단위 응답
- **내결함성**: 부분 장애에도 정상 동작

## 해결 방법 1: Multi-master Replication

### 동작 방식

- 여러 데이터베이스 서버에 auto_increment 활용
- 각 서버는 서버 수(k)만큼 ID 증가
- 서버 1: 1, 3, 5, 7, 9, ...
- 서버 2: 2, 4, 6, 8, 10, ...

[다이어그램 Figure 7-2: Multi-master replication 구조]

- 두 개의 데이터베이스 서버가 각각 홀수(1,3,5...)와 짝수(2,4,6...) ID를 생성

### 장점 👍

- 데이터베이스의 auto_increment 기능 활용
- 데이터베이스 서버 수만큼 ID 확장 가능
- 일부 확장성 문제 해결

### 단점 👎

- **여러 데이터 센터로 확장하기 어려움**
- **여러 서버에서 시간 순서대로 ID가 증가하지 않음**
- **서버 추가/제거 시 확장이 어려움**

## 해결 방법 2: UUID (Universally Unique Identifier)

### 동작 방식

- 128비트 식별자 사용
- 각 웹 서버에서 독립적으로 생성
- 충돌 확률: 10억 개/초로 100년간 생성해도 50% 미만

```python
import uuid

# UUID 생성 예시
unique_id = uuid.uuid4()
print(unique_id)  # 09c93e62-50b4-468d-bf8a-c07e1040bfb2
```

[다이어그램 Figure 7-3: UUID 분산 생성 구조]

- 각 웹 서버가 독립적으로 UUID 생성기를 가지고 ID 생성

### 장점 👍

- **UUID 생성이 간단함**
- **서버 간 조율 불필요** - 동기화 문제 없음
- **매우 쉬운 확장** - 각 웹 서버가 독립적으로 ID 생성

### 단점 👎

- **128비트 (요구사항: 64비트)**
- **시간 순서대로 증가하지 않음**
- **숫자가 아닌 값 포함 가능** (하이픈, 문자)

## 해결 방법 3: Ticket Server

### 동작 방식

- 중앙집중식 auto_increment 데이터베이스 서버
- 모든 웹 서버가 티켓 서버에서 ID 요청
- Flickr에서 개발한 방식

[다이어그램 Figure 7-4: Ticket Server 중앙집중 구조]

- 여러 웹 서버가 중앙의 티켓 서버 DB에서 ID를 요청하는 구조

### 장점 👍

- **숫자형 ID 생성**
- **구현이 쉬움**
- **중소규모 애플리케이션에 적합**

### 단점 👎

- **단일 장애 지점 (SPOF)** - 티켓 서버 다운 시 전체 시스템 영향
- **여러 티켓 서버 운영 시 데이터 동기화 문제 발생**

## 해결 방법 4: Twitter Snowflake (최종 선택)

### 선택 이유

- 모든 요구사항을 만족하는 유일한 방안
- 대규모 분산 시스템에서 검증됨
- 높은 성능과 확장성 제공

### 핵심 아이디어

- **분할 정복**: 64비트 ID를 여러 섹션으로 분할
- **타임스탬프 기반**: 시간순 정렬 보장
- **분산 생성**: 각 머신이 독립적으로 생성

### 장점 👍

- **모든 요구사항 충족**: 유일성, 64비트, 숫자형, 시간순 정렬
- **뛰어난 확장성**: 분산 환경에서 초당 10,000개 이상 생성 가능
- **높은 성능**: 데이터베이스 조회 없이 메모리에서 생성

### 단점 및 고려사항 👎

- **시계 동기화 문제**: 서버 간 시간 불일치 시 ID 순서 문제 발생 가능
  - 해결: NTP (Network Time Protocol) 활용
- **멀티 코어/멀티 머신 환경**: 모든 서버가 동일한 시간을 갖는다고 가정하지만 항상 참이 아닐 수 있음

[다이어그램 Figure 7-5 & 7-6: Twitter Snowflake 64비트 구조]

- 64비트를 Sign(1) + Timestamp(41) + Datacenter ID(5) + Machine ID(5) + Sequence(12)로 분할
- Datacenter ID와 Machine ID는 시작 시 고정되고, Timestamp와 Sequence는 동적으로 생성됨

## Snowflake 구조 상세 분석

### 64비트 ID 구성요소

```
┌─────────┬─────────────────────────┬─────────────┬─────────────┬─────────────────┐
│ Sign(1) │     Timestamp(41)       │Datacenter(5)│ Machine(5)  │  Sequence(12)   │
└─────────┴─────────────────────────┴─────────────┴─────────────┴─────────────────┘
```

### 각 섹션별 상세 설명

| 섹션                    | 비트수 | 설명               | 범위/용량         |
| ----------------------- | ------ | ------------------ | ----------------- |
| **Sign bit**      | 1      | 부호 비트 (항상 0) | 양수 보장         |
| **Timestamp**     | 41     | 에포크 이후 밀리초 | ~69년 사용 가능   |
| **Datacenter ID** | 5      | 데이터센터 식별자  | 32개 데이터센터   |
| **Machine ID**    | 5      | 머신 식별자        | 데이터센터당 32대 |
| **Sequence**      | 12     | 밀리초당 시퀀스    | 밀리초당 4,096개  |

### 생성 용량 계산

- **이론적 최대**: 1밀리초당 4,096개 × 1,000밀리초 = 초당 409만 6천 개
- **단일 머신**: 초당 최대 409만 개
- **실제 운영**: 여러 머신 분산으로 더 높은 처리량 가능

### ID 생성 프로세스 예시

```
시간: 2024-01-15 10:30:45.123
Datacenter: 1
Machine: 5
Sequence: 0

생성된 ID:
┌─┬─────────────────────────────────────────┬─────┬─────┬────────────┐
│0│1642234245123 (타임스탬프)                │00001│00101│000000000000│
└─┴─────────────────────────────────────────┴─────┴─────┴────────────┘
```

동일 밀리초에 여러 요청:

- 첫 번째 ID: ...00000000000000
- 두 번째 ID: ...00000000000001
- 세 번째 ID: ...00000000000010
- ...
- 4,096번째 ID: ...111111111111

### ID에서 타임스탬프 추출하기

[다이어그램 Figure 7-7: 이진수를 UTC로 변환]

```python
# ID에서 타임스탬프 추출 예시
# ID의 타임스탬프 부분을 오른쪽으로 22비트 시프트
timestamp_ms = (id >> 22) + epoch
# UTC 시간으로 변환
from datetime import datetime
utc_time = datetime.utcfromtimestamp(timestamp_ms / 1000.0)
```

## 추가 고려사항

### 1. 시계 동기화 (Clock Synchronization)

```bash
# NTP를 통한 시계 동기화
sudo ntpdate -s time.nist.gov
```

- **문제**: 서버 간 시계 불일치로 인한 ID 순서 문제
- **해결**: NTP (Network Time Protocol) 활용
- **대안**: 논리적 시계 (Logical Clock) 사용

### 2. 섹션 길이 튜닝

- **저동시성 + 장기간**: 더 많은 타임스탬프 비트
- **고동시성 + 단기간**: 더 많은 시퀀스 비트
- **지역별 서비스**: 더 적은 데이터센터 비트

### 3. 고가용성 보장

- **다중 ID 생성 서버**: 장애 대비 중복 운영
- **로드 밸런싱**: ID 생성 요청 분산
- **모니터링**: ID 생성 지연 및 오류 감지

## 핵심 인사이트 및 배울 점

### 🎯 시스템 설계 원칙

1. **Trade-off 분석의 중요성**
   
   - 각 방법마다 고유한 장단점 존재
   - 요구사항에 맞는 최적해 선택 필요
2. **분할 정복 (Divide & Conquer)**
   
   - 복잡한 문제를 작은 부분으로 나누어 해결
   - Snowflake의 64비트 분할 전략
3. **확장성 vs 복잡성**
   
   - 단순한 해법(Ticket Server)은 확장성 제한
   - 복잡한 해법(Snowflake)은 높은 확장성 제공

### 💡 기술적 배울 점

1. **분산 시스템에서의 합의 문제**
   
   - 전역 상태 없이 유일성 보장하는 방법
   - 각 노드의 독립적 의사결정
   - CAP 정리와 일관성 보장
2. **시간의 중요성**
   
   - 분산 시스템에서 시간 동기화 필수
   - 논리적 순서 vs 물리적 시간
   - Clock skew 문제 및 해결 방안
3. **비트 레벨 최적화**
   
   - 제한된 공간에서 최대 정보 담기
   - 각 비트의 의미와 활용 방안
   - 2^n 범위 활용의 효율성
4. **성능 최적화 기법**
   
   - 데이터베이스 조회 없이 메모리에서 생성

## 부록: 구현 예시 (의사 코드)

```python
class SnowflakeIDGenerator:
    def __init__(self, datacenter_id, machine_id):
        self.datacenter_id = datacenter_id  # 5 bits
        self.machine_id = machine_id        # 5 bits
        self.sequence = 0                   # 12 bits
        self.last_timestamp = -1
      
        # Custom epoch (예: 2024-01-01 00:00:00)
        self.epoch = 1704067200000
      
    def generate_id(self):
        timestamp = self._current_timestamp()
      
        # 동일 밀리초 내 처리
        if timestamp == self.last_timestamp:
            self.sequence = (self.sequence + 1) & 0xFFF  # 12 bits
          
            # 시퀀스 오버플로우 시 다음 밀리초 대기
            if self.sequence == 0:
                timestamp = self._wait_next_millis(timestamp)
        else:
            self.sequence = 0
          
        self.last_timestamp = timestamp
      
        # ID 조합: timestamp(41) | datacenter(5) | machine(5) | sequence(12)
        id = ((timestamp - self.epoch) << 22) | \
             (self.datacenter_id << 17) | \
             (self.machine_id << 12) | \
             self.sequence
           
        return id
  
    def _current_timestamp(self):
        return int(time.time() * 1000)  # 밀리초
  
    def _wait_next_millis(self, last_timestamp):
        timestamp = self._current_timestamp()
        while timestamp <= last_timestamp:
            timestamp = self._current_timestamp()
        return timestamp

# 사용 예시
generator = SnowflakeIDGenerator(datacenter_id=1, machine_id=5)
unique_id = generator.generate_id()
print(f"Generated ID: {unique_id}")
```

## Q&A: 자주 묻는 질문

### Q1: 시계가 역행하면 어떻게 되나요?

**A**: 시계가 역행하면 ID 중복이 발생할 수 있습니다. 해결책:

- 에러를 발생시키고 관리자에게 알림
- 시계가 정상화될 때까지 대기
- 논리적 시계 사용 (벡터 시계 등)

### Q2: 41비트 타임스탬프가 부족하면?

**A**: 약 69년 후 고갈됩니다. 해결책:

- 새로운 epoch 시작 시점 설정
- 비트 할당 재조정 (예: 시퀀스 감소, 타임스탬프 증가)
- 128비트 ID로 마이그레이션

### Q3: 데이터센터나 머신 ID는 어떻게 할당하나요?

**A**:

- 설정 파일에 하드코딩
- 환경 변수로 주입
- 중앙 설정 관리 시스템 (Consul, etcd) 활용
- 자동 할당 시스템 구축
